1. 平台是做什么的

面向内容运营的「小红书风格图文」批量生产平台：导入选题 Query → AI 取证/写正文/ 分 6 页文案/生成 6 张竖版卡片图（3:4）→ 规则机+视觉审核 → 人工核查/审图 → 签发导出。 三种生产模式：general（通用科普）、single（单一产品实测，图生图保外观）、 compare（两主体对比，双实景参考图生图）。

设计原则：AI 只做创作段，业务调度、校验、审核、记账全部在后端确定性代码里； 每个 LLM/生图调用可 mock、可重试、有幂等键、有成本记账。

5. 核心机制详解

5.1 双路径流水线（最重要的设计）

src/pipeline/orchestrator.py： - NODES（直连 13 节点，定义在 nodes.py:31）：task_import → entity_bind → evidence_build → draft_gen → rule_check → page_split → asset_gen → ocr_read → cross_check → risk_classify → review_queue → batch_signoff → publish_snapshot - NODES_AGENT（Agent 路径，生产默认）：创作段 6 节点（entity_bind/evidence_build/ draft_gen/page_split/asset_gen/ocr_read）收敛为 1 个 agent_production，并新增 ref_seed / text_check / ref_collect 三个关卡节点：task_import → ref_seed → text_check → ref_collect → agent_production → rule_check → cross_check → risk_classify → review_queue → batch_signoff → publish_snapshot （2026-09-07 两段式实景搜图，吸收 8002 分叉栈设计： ①ref_seed（src/pipeline/ref_seed.py，自动、无人工关）素材库复用+按主体搜图 +OCR 初筛（复用 ref_collect._collect_candidates），落 selection_status='text_ref' 反哺 text_check 起草（text_check._refs_feedback_section 注入段内容/位置不变， 无图零差异）；②text_check 人工关（awaiting_text）；③ref_collect 搜图②： 候选池=text_ref 叠加新搜（内容 hash 去重，text_ref 全部并入 candidate 不留 残留），人工确认关 awaiting_refs，keep→confirmed、其余→rejected； ④agent_production 读 confirmed 不变（refs_section 含「必须使用+图生图+ 文案与参考图画面一致」）。确认后幂等续跑机制不变；general 模式仍由 REF_FOR_GENERAL_ENABLED（默认 false）门控，false 时 ref_seed/ref_collect 照旧跳过、整条链路零差异。前端节点条由 /api/meta/nodes 读 progress.node_order()，自动跟随。） - 开关 AGENT_PIPELINE_ENABLED（.env），false 秒切回直连路径兜底。 - 两路径同源提示词：都从 get_effective_prompt(kind, mode, owner_id) 取词 （解析顺序：用户自定义 → admin 系统覆盖 → 代码默认）。 ⚠️ 历史教训：同一要求必须同时注入所有路径（详见 5.3）。

5.3 提示词库体系（改提示词必读）

2026-09-03 阶段2重构后：全部生成类提示词的单一事实来源是 skills/ 目录 （10 个 skill 包），由 src/gateway/skill_loader.py 统一取词； prompt_versions.py 常量名与取值不变（内部改从 skill_loader 读）， 三级覆盖语义（用户自定义 → admin 系统覆盖 → 代码默认）原样保留。关键点：

  • skill 包结构：skills/<name>/SKILL.md（frontmatter：name/description/notes + 正文模板）+ 片段文件 <frag>.txt（可带一层子目录，如 prompts/general.txt）； 列表型片段（如 6 条排版轮换）单文件内以单独一行 --- 分隔， 用 fragment_list() 读取。
  • 正文写作的「人设与真人感+信息密度」共享段（skills/draft-write/shared_persona.txt） 必须三条路径都注入：①直连 draft_gen（nodes.py）②Agent 路径 （agent_production.py 取词后 append）③text_check 起草（用户在核查关卡看到的草稿）。 注入条件不变：template == default_prompt(...) 时才追加——用户自定义模板代表 显式意图，不覆盖（防负优化）。
  • 图上文案字数契约（2026-09 起）：每页 80-130 字、六页差≤40、每页 1-2 个具体 信息点。已收敛为单点 skills/page-split/contract.txt（PAGE_MIN_CHARS 等 5 个键，skill_loader 顶部解析成常量）——page-split/prompt-analyze 提示词、 nodes._balance_issue 硬校验（不达标自动带意见重试一次）、 agent_production._AGENT_INSTRUCTIONS 合规红线段全部从该单点渲染，连同 regen.py 定点重写的均衡参照段共 8 处消费方同吃一源 （血泪史：此前要 7 处手工同步，漏一处就出阴阳口径）。改字数口径只改 contract.txt，并跑 tests/unit/test_page_balance.py 守卫断言。
  • 提示词类重构的兜底验证：scripts/verify_skill_equivalence.py——重构前 --baseline（快照全部取词/渲染结果），重构后 --verify（逐键对比零差异 退出码 0，另对撞 contract.txt 解析出的契约常量）。顺序不可颠倒。
  • 测试里有「守卫断言」锁定关键提示词片段（如 test_absorb_8002 锁「胶囊」 「CAPSULE」、test_page_balance 锁字数）——改提示词先跑相关测试。

5.4 生图与视觉闭环

  • 生图走 MCP image_gen → src/gateway/image_gen.py：IMAGE_GEN_CHANNELS 通道轮询（fusion,linkai,moacode），IMAGE_GEN_PARALLEL=6 并发，size 1152x1536 （3:4），quality=high；MOCK_IMAGE_GEN=true 时返回占位图（联调用，不花钱）。
  • compare/single 模式：确认后的实景参考图作为图生图 references 传入， 6 页实景用法必须错开（按页轮播分配，铁律，e6c550b）。
  • 落库后：本地化/去重/hash/尺寸校验 → OCR 逐页比对（错字/漏字自动重生成， garble_regen loop）→ qwen-vl-max 视觉审核（图文一致/主体匹配 subject_mismatch）。

5.5 实时流与记账

  • src/stream/bus.py 进程内事件总线 → /api/stream/events（SSE）：节点开始/完成/ 失败（含 traceback）、Agent 流式增量、生图进度。前端监控页实时渲染。
  • 成本：tool_ledger + cost_tracker，节点事件记 cost_estimate_cny， /api/admin/costs 汇总。Agent 工具成本经 HTTP 回调合并进节点。

5.6 dsh 迁移要点（Nanobot → dsh_serve，2026-09 重构）

完整验证记录见 docs/dsh-spike-验证记录.md（Go/No-Go 七项 + 三轮真实链路补测）， 组件细节与配置全表见 dsh_serve/README.md。接手必记的几条：

  1. 薄层形态：dsh（DeepSeek Harness）没有原生 OpenAI 兼容端点（dsh web 是 浏览器 GUI 宿主，headless 不开端口），dsh_serve 是 Python FastAPI 薄层，经官方 SDK 常驻驱动 dsh --profile sdk 子进程。POST /v1/chat/completions + session_id + SSE（delta.content / delta.reasoning_content / 末尾 usage chunk） 与 Nanobot 1:1——后端 nanobot_client 只改 NANOBOT_BASE_URL 指向 :8901 即切换。
  2. max_tokens 含 reasoning_tokens（本轮最大的坑）：deepseek 推理模型的输出 预算把推理 token 算在内——旧值 8192 在 reasoningEffort=high + 长 prompt 下被 推理一轮吃光：正文 0 字符、0 次工具调用，turn/end reason=max-tokens （2026-09-05 真实任务事故，会话日志铁证）。现 DSH_MAX_TOKENS=32768； max-tokens 截断是显式失败形态（TruncatedOutputError）触发主备降级。 再遇 max-tokens 降级：先调低 DSH_REASONING_EFFORT 或继续上调上限。
  3. 跨进程会话恢复靠 transcript 镜像 + 别名 fork：dsh sdk profile 不支持跨进程 冷恢复（重启后同 session_id 会被持久化层以 "id collision" 拒绝）。薄层每轮 成功后在 $DSH_HOME/dsh-serve/transcripts/ 记录 user/assistant 正文，撞碰撞时 自动 fork 新别名 <sid>--r<N>、把历史作前言拼进 prompt 重发（碰撞在 turn 开始即失败，不耗 token，调用方无感知）。历史只保留最近 20000 字符—— 纠错重问（近几轮）完全够用，跨长任务多节点编排记忆不保证完整。
  4. MCP 冷启动 52-88s：qvp_mcp import 慢（litellm 远程价表拉取 + OneDrive 云盘 IO），逼近/超过 MCP SDK 60s 握手上限，首挂靠自动重连 1-2 分钟内补上。缓解： MCP_EXTRA_ENV 里加 LITELLM_LOCAL_MODEL_COST_MAP=true，并把 DSH_INITIALIZE_TIMEOUT_SECONDS 提到 120（默认已是）。
  5. 内置 web_search 已禁用：dsh base 自带 web_search/web_fetch，不显式点名时 模型会用错工具（补测实证）。serve patch 默认禁用（tool-web 行 disabled）， 检索/生图/OCR 只存在 mcp__qvp__* 形态；生产 prompt 里也要明确点名工具名。
  6. 钉版纪律：dsh 处于 developer preview，官方明示 "THERE WILL BE COMPATIBILITY-BREAKING CHANGES"——版本钉死 0.1.2-rc.1 （deploy/Dockerfile.dsh 的 ARG DSH_VERSION），升级前必须重跑 spike 验证清单 并回归 dsh_serve 单测。
  7. failover 薄层自做（2026-09-10 起三级）：dsh 原生只有同路由重试 （max 5 次），不跨模型切换。三级线路：主 DeepSeek 官方 deepseek-v4-flash （价约 pro 1/3）→ 备1 Kimi 开放平台 kimi-k3（openai-completions， api.moonshot.cn，按量付费）→ 备2 Kimi Code 会员 k3（anthropic-messages， api.kimi.com/coding；KIMI_CODE_API_KEY 空则该级自动禁用）。主路由失败 （连接错误/子进程崩溃/超时/max-tokens 截断/空响应/拒答词命中）时同 session 逐级整轮重发。流式纪律：reasoning 实时透传，content/usage 缓冲到当轮质检 通过才 flush——客户端永不见半截正文。代价：降级轮首 token 延迟 = 前级整轮 耗时（结构性成本，暂接受）。后端直连路径 src/gateway/failover.py 同为三级 （kimi_code_api_key 默认空=禁用第三级）。
  8. profiles/node_modules 半成品处置：主备两个 dsh 子进程并发首启竞争 $DSH_HOME/profiles/node_modules.lock（组件内已加 _boot_lock 串行化）； 首启超时被强杀后 profiles/node_modules 留半成品，下次启动报 "not a dsh-managed module proxy"——删掉该目录（或整个 dsh-home）即恢复。
  9. 容错语义对齐 Nanobot：MCP 挂不上不阻断启动（failOnStartupError:false， 模型侧感知降级）；/health 的 mcp.command_exists 可事前发现 MCP_COMMAND 路径配错。qvp_mcp 的配额/成本回调是 fail-open——后端不在时工具照常返回。

14. 已知坑与经验（血泪史精选）

  1. Windows 本地：必须用 .venv/Scripts/python.exe（系统 python 没装依赖）； Git Bash 调 curl 上传文件用相对路径（/tmp 路径转换会失败）；中文 query 参数要 URL 编码。仓库部分文件 CRLF，git 会警告，无碍。
  2. MCP 环境缓存：qvp_mcp 是创作网关的 stdio 子进程，读 .env 发生在网关 启动拉起子进程那一刻——改配置后「重启后端」不够，要重启创作网关 （Nanobot/dsh_serve 同理）。
  3. 提示词多路径：任何写作类要求都要检查 5.3 列出的全部注入点，否则只改一处 不生效（生产走 Agent 路径）。字数契约已单点化（contract.txt），其余提示词 改动先想「还有哪条路径也吃这段词」。
  4. 排障顺序：docker logs qvp2-app（或本地 uvicorn 输出）→ SSE /api/stream/state（含 error/debug/trace，比库里 error_class 详细）→ 创作网关会话日志：Nanobot 在 ~/.nanobot/workspace/sessions/*.jsonl； dsh 在 $DSH_HOME/sessions/**/session.jsonl.zstd（zstd 压缩，用 dsh_serve/analyze_session.py 解析——余额不足、max-tokens 截断这类真因都在这）。
  5. 图上文案字数：模型偶尔越界 ±5 字，硬校验会自动重试一次，仍越界保留较轻一版 交人工审图兜底——不要为此加死循环。
  6. 生图成本：一条任务 6-8 张上限（配额硬限），余额/限流错误会以任务失败收场， 报错现在会带 Agent 备注（1eb6c0b）。
  7. docker run 裸命令调 qvp3 镜像会触发 ENTRYPOINT（entrypoint.dsh.sh 会起 init_db→dsh_serve→后端一整套）——只想进容器调试必须 docker run --entrypoint sh ...，否则端口/进程一团乱。
  8. MCP_COMMAND 必须全路径：dsh_serve 按文件路径判定存在性 （/health 的 mcp.command_exists），写 python 这种靠 PATH 解析的名字会 判不存在、MCP 静默不挂；容器内用 /usr/local/bin/python，本地用 .venv/Scripts/python.exe 全路径。
  9. node alpine 与 Debian glibc 不匹配：node:*-alpine 是 musl libc，二进制 COPY 进 python:3.12-slim（Debian）跑不起来（exit 127）——应用镜像必须用 node:24-slim 做复制源（deploy/Dockerfile.dsh 头部注释有写）。
  10. execute_node 已改三段式短事务（2026-09）：旧版一个事务跑完整个节点， 长外部 I/O 期间连接被中间层掐断、收尾 commit 抛 InterfaceError 拖垮节点； 现为「短事务落 started → 节点裸跑 → 新短事务回写 finished/failed」。 取消语义随之改变：CancelledError 显式捕获后删除本次 started 事件 （等价旧版"取消即回滚无残留"，重试会重新执行）；进程崩溃会残留 started 事件（幂等层把未完成事件视为可重跑，删旧重建）——任务详情短暂显示 running 属预期，不要误判为卡死。
  11. 能力工具内嵌 LLM 调用叠加 Agent 外层推理，单工具耗时可达 400+s—— 调用方超时需 ≥600s（生产链路 3000s 已够）；curl 超时丢响应不丢结果， 同 session 追问可取回。
