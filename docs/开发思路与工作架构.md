> 版本：2026-08-25 ｜ 对应代码：main 分支（77ebff2）
> 本文是平台的顶层设计文档：为什么这样设计、各部分如何协作、在哪里扩展。

---

## 一、开发思路（核心理念）

### 1.1 一句话定位

**「业务调度层 + 创作大 Agent」双层架构**：FastAPI 后端管一切确定性的事
（参数校验、任务入库、队列调度、配额、成本、重试、状态持久化、审核、导出），
一次 OpenAI 兼容流式调用把整个创作过程交给 Nanobot Agent
（检索取证 → 风格判定 → 正文 → 分页 → 生图 → OCR 自检），
后端只对 Agent 的产出做**确定性收尾与质检**。

### 1.2 五条设计原则

| 原则 | 落地方式 |
|---|---|
| **确定性优先** | AI 只出现在「创作」环节；校验/入库/状态机/审核/导出全部是确定性代码。Agent 输出必须过 JSON 契约校验，不合格带错误同 session 纠错重问一次，仍不合格 → 节点失败 |
| **后端权威** | MCP 工具配额、成本台账、任务状态都以后端为准（内存权威 + HTTP 回调），Agent/MCP 进程崩溃或残留状态都不会把系统锁死 |
| **幂等可重放** | 任务幂等键去重、节点级幂等跳过（已完成节点重试不重跑）、迁移 SQL 全部幂等；中断/失败/驳回的任务都能安全重试 |
| **可降级可回退** | 文本模型 DeepSeek 主 + Kimi 备双活；`AGENT_PIPELINE_ENABLED=false` 一键切回 13 节点直连路径；MCP 生图并行度/超时/重试参数化，按环境调优 |
| **全程可观测** | SSE 实时事件流（节点进度 + Agent 流式输出 token 计数 + 工具阶段提示），成本按 任务×节点×模型 三维记账，审计日志不可删 |

### 1.3 演进路线（为什么长成现在这样）

1. **直连路径（13 节点）**：entity_bind → evidence_build → … → publish_snapshot，
   每个 AI 环节一次 LLM 调用，链路长、上下文割裂 → 保留作回退路径
2. **Nanobot 全链 Agent（8 节点）**：中间 6 个 AI 节点合并为一个大节点
   `agent_production`，Agent 带工具编排整个创作，上下文完整、质量与速度双升
   （单任务 560s → 277s，吞吐 26-52 条/小时 @并发 2-4）
3. **风格自适应 + 组合生成导入**：内容风格（5 类）与图片整体视觉风格（8 类）
   由 Agent 按 query + 检索信息自适应判定、多适配随机选；组合导入按
   「query × 泛化问题池」批量随机组合生产
4. **容器化独立部署**：qvp2 栈（vpstest04 :8003），与旧栈完全隔离

### 关键点

- **一次 Agent 调用 = 原来六个 AI 节点**：Agent 在同一 session 内带上下文完成
  检索→判定→写作→分图→生图→自检，后端 `nanobot_client` 流式读取并节流上报监控
- **MCP 工具不是自由调用**：每次调用先 HTTP 回后端扣配额
  （web_search≤3 / image_search≤3 / image≤8 / ocr≤8，节点开始时重置），
  每次实际使用再回调记账（工具名+成本+参数摘要 → node_events）
- **8 节点 Agent 路径**：task_import → **agent_production** → rule_check →
  cross_check → risk_classify → review_queue → batch_signoff → publish_snapshot
  （后 5 个是确定性质检/审核节点，与直连路径共用）
- **双路径开关**：`AGENT_PIPELINE_ENABLED`（.env）。false 时编排器走原 13 节点
  直连路径，`/api/meta/nodes` 同步切换，前端节点条自适应

## 四、任务生命周期与数据流

```
导入(3种) ──► 幂等键去重入库(draft) ──► 队列(自适应并发 2→4, 可手工中断)
   │
   ▼
task_import ──► agent_production（一次 Nanobot 流式调用）
                   1. web_search 检索证据（配额内 1-2 次）
                   2. 风格判定：内容风格(5类) + 图片视觉风格(8类库)
                      · 依据 query + 检索信息，多适配随机选
                      · 组合导入显式指定的风格不覆盖
                   3. 正文 400-700 字（禁词红线 + 字数硬约束）
                   4. 6 页分页文案
                   5. generate_images 批量生图（模板风格句替换为所选视觉风格，
                      单图3次重试，跨页去重复生，产出即本地化）
                   6. OCR 默认跳过（后端兜底并行补齐）
                   └─ 输出 JSON 契约（content_style/image_style 一并回填任务）
   │
   ▼ 后端确定性收尾：图片本地化/哈希/尺寸校验 → 原子落库
rule_check(禁词/字数) ──► cross_check(图文一致性, OCR 对撞) ──► risk_classify(红黄绿)
   │
   ▼
review_queue ──► 人工审核（A/B/C 任一角色；驳回可整篇重生成或⚑定点重生成）
   │                                      批次会签 → publish_snapshot
   ▼
approved ──► 导出（任务式打包 ZIP，每10条一包，图片统一 1152×1536）
```

**三种导入方式**：

| 方式 | 入口 | 说明 |
|---|---|---|
| 逐行文本 | `POST /api/tasks/import_queries` | 每行一条 query，风格由 Agent 生产时自适应判定 |
| CSV 文件 | `POST /api/tasks/import` | query/mode/content_type/platform 列 |
| **组合生成** | `POST /api/tasks/import_combo` | 原始 query × 泛化问题池（`analyze_query` 智能分析生成、可手工增删）× 风格/垂类条件 × N 条 → 随机抽 N 个角度各成一条任务，重复组合幂等跳过 |

## 五、可靠性与运维设计

### 5.1 失败处理矩阵

| 故障 | 行为 |
|---|---|
| DeepSeek 超时 | 自动切 Kimi k3（failover，degraded 标记） |
| Agent 输出不合契约 | 同 session 纠错重问 1 次，仍失败 → 节点失败 → 任务 failed |
| Nanobot 不可达 | agent_production 启动即检，失败提示或切直连路径 |
| 单张生图超时 | MCP 内 3 次重试（间隔递增），整批容错聚合，明确报失败页 |
| 任务生产中卡住 | 监控页手工中断（cancel 协程，node_events 自动回滚），可幂等重试 |
| 驳回 | 整篇重生成（驳回理由注入提示词）或定点重生成（⚑标记页，其余保留） |
| 容器内 Nanobot 挂 | entrypoint 守护循环 2s 自动拉起 |

### 5.2 并发与性能

- 自适应并发限流：`INITIAL/MAX_CONCURRENCY`（当前 2/4），Nanobot 并发对齐 4
- 生图批内并行 `IMAGE_GEN_PARALLEL`（本地 2 / 服务器 1-2），批间隔防限流
- OCR：Agent 自检优先，缺页后端 3 路信号量并行兜底
- 实测：本地单任务 ~277s（↓51%）；服务器受 linkai 对该 IP 限速 ~24 分钟/任务

### 5.3 成本口径

文本 usage（流式缺 usage 时按 字符/1.7 估算）+ MCP 工具回调台账（检索/搜图/生图/OCR
单价配置化）→ node_events.cost_estimate_cny；`/api/admin/costs` 三维拆分。

### 5.4 部署形态

| 环境 | 形态 | 地址 |
|---|---|---|
| 本地开发 | start-all.sh 一键启停（Docker Desktop + qvp-postgres:5433 + nanobot:8900 + uvicorn） | 127.0.0.1:8003 |
| **vpstest04 生产** | qvp2 容器栈：app（后端+Nanobot+MCP 同容器）+ postgres:16，独立网络/卷/项目 | http://117.34.118.115:8003 |

更新部署三步：`git archive HEAD` 打包 → 解压到 `~/qvp2` → `docker compose up -d --build`
（迁移幂等自动应用）。详见 `docs/改造说明-Nanobot全链Agent.md` 第八节。

## 六、数据模型要点（24 表，迁移 001-008）

- **任务主链**：tasks（含组合导入 4 字段 source_query/supplement_question/
  gen_style/gen_category + 风格自适应 gen_image_style）→ drafts → page_copies →
  assets（ai_generated/official，origin_url 追溯）→ ocr_results
- **事实链**：claims → evidence（P1/P2 信源分级）
- **质检链**：rule_results / cross_checks / risk_classifications
- **审核链**：review_sessions / review_actions / issues / reject_marks（定点驳回）/
  batches / batch_members / approvals / publish_snapshots
- **平台链**：users（A/B/C 角色，试运行期全员全角色）/ organizations /
  prompt_templates（(stage,mode,owner) 三级：用户自定义→admin覆盖→内置）/
  activity_logs（审计，不可删）/ node_events（节点事件+成本）

## 七、测试与质量

- **150 项 pytest 全绿**：单元（契约解析/配额/批处理/组合解析/风格库）+
  集成（双路径流水线/CRUD 级联删除/组合导入/取消重试），测试库 qvp_test 隔离
- 每次交付前：pytest 回归 → 本地真实任务冒烟 → 自 review 结果自洽 → 用户 web 验收
- 冒烟脚本：`scripts/smoke_agent.py / smoke_review.py / verify_monitor.py`
